# Joined read fixture — source prepared, execution held

This successor requires baseline full-loader platform PASS and independent
review of the eventual modern runner/seed before execution. It does not change
production protocols, routes, authorities, keys, activation or version0.186.0.

`tls_vm_tests.rs` connects the real protected publisher/encrypted loader,
`ExactObjectServer::serve_connection`, mandatory-client-auth `ServerTls`, and
the real `ExactObjectClient` with its SQLite one-use journal. Root setup uses
the existing actual ledger create/retain APIs with explicitly synthetic
in-memory storage, then generates guest-only TLS/Ed25519 material before
publication. No synthetic loader or supplied admission flag is used.

`tls-guest.sh` uses distinct reader2000/verifier2001 processes. This is functional
isolation, not physical off-NUC provenance. The AWS process reads the exact
selected object over loopback HTTP through the real bounded FIFO adapter.
`s3-responder.py` is only a protocol responder; it does not authenticate or
qualify Garage, legal hold, retention, backend TLS or deployment provenance.
All request headers and private material remain inside the disposable guest.

The four cases require successful bytes; full TLS-configuration binding
mismatch with zero GETs; same-length corrupt backend bytes; and backend
disconnect. The latter cases must deny, preserve a started/terminal journal
record, and deny the same request after reopening. The responder rejects any
second GET. Each case preserves the manager publication and full ledger bytes;
non-secret journals remain inside the guest for evidence selection. Existing
TLS tests separately cover actual TLS response truncation/unclean closure.

## Offline AWS install guard

The seed must include the exact71 signed Fedora44 RPM closure under
`aws-rpms`, with repository metadata generated by the independently verified
`createrepo_c` public preparation. It also carries `aws-guest-install.sh`,
`aws-transaction-guard.py`, `s3-responder.py`, and the exact stripped adapter.
No virtual NIC or network-enabled installation is permitted.

The installer checks the fixed complete payload manifest hash, all71 payload
hashes and all signatures against only the approved Fedora44 key. DNF resolves
`awscli2` against the actual installed guest RPM database and stores, rather
than runs, its transaction. The guard accepts only version1.0 with new Install
actions from that local repository, exact NEVRA/payload joins, no unknown
fields or duplicates, and no already-installed package name. It does not
implement dependency resolution. The actual stored DNF format was checked
against upstream5.4.2.0 `transaction_sr.cpp` and the retained public QEMU plan.

The selected new RPMs undergo `rpm --test -ivh` before exact DNF replay, without
skip/ignore/replace options. The installed set must remain unchanged after
planning/testing and equal precisely its prior set plus the approved new rows
after installation. Systemd executable/control/credential-tool hashes must
also remain identical. This protects the qualified systemd/kernel/core package
versions; it does not assert that signed package scripts have no effects in
the disposable guest. Unsupported guest tooling/solver results deny rather
than selecting a different package closure.

Current evidence: native all-features compile and transport-only regressions
in `evidence/joined-native-compile.txt`; six pure transaction-guard tests. The
guest installer, joined runner, actual AWS/FIFO exchange and loaded-server
matrix remain unexecuted. Public preparation metadata is not formal custody
evidence and no booted image may be exported.
